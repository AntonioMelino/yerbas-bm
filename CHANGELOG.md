# CHANGELOG.md — Yerbas BM

## [2026-07-27] - Feature: product-image-upload
- Rama: feature/product-image-upload
- Qué se hizo: Implementada la subida de imágenes de producto a Supabase Storage (bucket público `product-images`, sección 9 de CONTEXTO.md). Se agregó `IProductImageStorage` (Application) y su implementación `SupabaseProductImageStorage` (Infrastructure), que sube el archivo llamando directamente a la Storage REST API de Supabase vía `HttpClient` (sin sumar el SDK completo `supabase-csharp`, ya que solo hace falta subir un archivo). `POST /api/products` y `PUT /api/products/{id}` pasan a recibir `multipart/form-data`: la imagen (`Image`) es obligatoria al crear y opcional al actualizar (si no se envía, se conserva la imagen actual). Antes de subir, se valida tamaño (máx. 2 MB), Content-Type declarado (JPG/PNG/WebP) y los primeros bytes del archivo (magic bytes), para no confiar ciegamente en el Content-Type que manda el cliente. Cada imagen se sube con un nombre único (GUID) para evitar colisiones. Se probó el flujo completo contra el bucket real: creación con imagen (201, URL pública accesible), actualización sin imagen nueva (conserva la existente), y los tres rechazos esperados (archivo con contenido que no coincide con el Content-Type declarado, archivo que supera 2 MB, y sin token → 401 ya cubierto por `[Authorize]`).
- Bug encontrado corriendo contra Supabase real: `Supabase:Url` apuntaba a la URL del REST API (`.../rest/v1/`, tal como la muestra el dashboard de Supabase en otra sección) en vez de la URL base del proyecto, lo que rompía el path del Storage API y devolvía un 404 confuso (`PGRST125 Invalid path specified in request URL`, un código de error de PostgREST, pista de que la request ni siquiera llegaba al Storage API). Se corrigió el secret y además se agregó una normalización defensiva en `SupabaseProductImageStorage` que recorta un sufijo `/rest/v1` si alguien vuelve a configurar mal la URL.
- Archivos principales afectados: `backend/YerbasBM.Application/Interfaces/IProductImageStorage.cs`, `backend/YerbasBM.Application/Common/ProductImageValidator.cs`, `backend/YerbasBM.Infrastructure/Services/SupabaseProductImageStorage.cs`, `backend/YerbasBM.API/Requests/{CreateProductFormRequest,UpdateProductFormRequest}.cs`, `backend/YerbasBM.API/Controllers/ProductsController.cs`, `backend/YerbasBM.API/Program.cs`, `backend/YerbasBM.API/appsettings.json`, `backend/YerbasBM.Application/DTOs/{CreateProductDto,UpdateProductDto}.cs`

## [2026-07-27] - Verificación: integración contra base real (Supabase)
- Rama: feature/verify-real-db-integration
- Qué se hizo: Todo el trabajo anterior (categories-crud, products-crud, admin-auth-jwt) se había verificado solo compilando o contra una base sin configurar; esta fue la primera prueba end-to-end contra la instancia real de Supabase. No se encontraron bugs ni comportamientos inesperados corriendo contra la base real: el fallback de `Jwt:Key` agregado en la feature anterior no se activó (confirma que los user-secrets cargan correctamente) y no hubo divergencias entre el esquema de EF Core y el de Supabase.

## [2026-07-26] - Feature: admin-auth-jwt
- Rama: feature/admin-auth-jwt
- Qué se hizo: Implementada la autenticación del panel admin con JWT (único rol autenticado del sistema, sin registro de clientes — sección 10 de CONTEXTO.md). Se agregaron los DTOs (`LoginDto`, `LoginResponseDto`), las interfaces `IAuthService`/`IAdminUserRepository`/`ITokenGenerator`, el repositorio EF Core (`AdminUserRepository`), el generador de tokens (`JwtTokenGenerator`, HMAC-SHA256 vía `System.IdentityModel.Tokens.Jwt`) y el servicio de negocio (`AuthService`, valida contraseña con BCrypt). Se expuso `AuthController` con `POST /api/auth/login`. Las mutaciones de admin existentes (`POST`/`PUT`/`DELETE` de `CategoriesController` y `ProductsController`) quedaron protegidas con `[Authorize]`; los `GET` siguen públicos. Se agregó `AdminUserSeeder`, que crea el único admin la primera vez que la API arranca con `admin_users` vacía y `Seed:AdminUsername`/`Seed:AdminPassword` configurados (no hay endpoint de registro). Durante las pruebas se detectó y corrigió un bug: con `Jwt:Key` sin configurar, el middleware de autenticación rompía con 500 **cualquier** request (incluido `/api/health`, que no depende de la base) — se resolvió generando una clave de firma aleatoria efímera como fallback cuando no hay `Jwt:Key`, sin habilitar por eso el login (que sigue requiriendo una key real vía `JwtTokenGenerator`). Se verificó que el proyecto compila sin errores y, en runtime sin base de datos configurada, que `/api/health` responde 200, `/api/categories` (GET) sigue público, y `POST /api/categories` sin token devuelve 401 antes de tocar la base.
- Archivos principales afectados: `backend/YerbasBM.Application/DTOs/{LoginDto,LoginResponseDto}.cs`, `backend/YerbasBM.Application/Interfaces/{IAuthService,IAdminUserRepository,ITokenGenerator}.cs`, `backend/YerbasBM.Application/Services/AuthService.cs`, `backend/YerbasBM.Infrastructure/Repositories/AdminUserRepository.cs`, `backend/YerbasBM.Infrastructure/Services/JwtTokenGenerator.cs`, `backend/YerbasBM.Infrastructure/Data/AdminUserSeeder.cs`, `backend/YerbasBM.API/Controllers/AuthController.cs`, `backend/YerbasBM.API/Controllers/{CategoriesController,ProductsController}.cs`, `backend/YerbasBM.API/Program.cs`, `backend/YerbasBM.API/appsettings.json`, `backend/README.md`
- Post-review: tras `security-reviewer`/`code-reviewer`, se corrigieron un bug (login sin manejar cuando falta `Jwt:Key`, ahora capturado y devuelve 500 seguro) y un hallazgo de seguridad HIGH (`Jwt:Key` sin mínimo de longitud, ahora exige 32 bytes/256 bits), y se agregó un log `Warning` al arrancar cuando `Jwt:Key` no está configurado. Quedan como pendientes no bloqueantes (documentados en sección 11 de CONTEXTO.md): rate limiting en el login y un timing side-channel que permite enumerar el username.
